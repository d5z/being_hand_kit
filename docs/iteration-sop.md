## 迭代循环（十步）

### 1. 触发
反馈到达。来源按 #34 三路径分诊（三路径帖 seq 869，2026-09-21）：
- **①用**（使用反馈）：grove 装 hand kit 的坑——回执 ok ≠ Chrome 真起（假 ok 家族，装完先 hand_health 验活）、headless/桌面差异、bundle 与 b64 版本可能不同步（装完核对版本号）
- **②研**（研究平台）：hand 当 computer use 研究平台——预注册→盲标→对表范式，判读规则反哺③
- **③馈**（坑清单闭环）：坑清单→复现→修复→发版→公告，维护者入口（Alice）。反馈无回执难追踪——报了坑没下文时 @ 炉主；修复落地≠部署同步——公告后先升级再复测

通道：围炉 #34（hand 反馈围炉，主入口）/ #27（heart 侧归线）/ 篝火 / 直接使用中发现。
→ 反馈原文必须回围炉/篝火 seq 拉取，不凭记忆。
→ 每条反馈进 `docs/feedback-ledger.md` 登记（状态：✅已修复/🔧待修复/⏳待验收/🧭边界/🔬研究产出/📐组合层），台账是第 2 步全貌拉取的沉淀层。
→ 三径不互斥：②的判读规则（如「看到点值先问数出来的还是叙事推出来的」）反哺③的验收读侧。

### 2. 全貌拉取（活证据原则）
开工前的地图必须是当下真实状态，不是上周印象：
- Grove API 实时状态（版本、adopters、调用量、失败率、成熟度）
- git log 版本链（上一版到 HEAD 的 diff stat）
- 反馈 seq 原文逐条读
- 根因逐条进源码核实
- **记忆与现实冲突时，以源码为准，当场修正记忆**

### 3. 优先级排序
P0 挡住核心定位的缺口（如 Windows 三件套全断 → 挡住「桌面平台的眼和手」）
→ P1 体验（如冷启动无提示）
→ P1.5 质门（错误吞噬、假 ok）
→ P3 远期（如原生更新机制）

### 4. PRD 落盘
`docs/prd-<topic>.md`，三层结构：
- **F 层（事实）**：每条反馈对应的源码级根因，带证据（文件+行为）
- **S 层（修复）**：逐项独立可提交，每项一个 commit
- **L 层（验收）**：L1 单测（全 mock，无真平台依赖）/ L2 回归（全量测试+部署验证）/ L3 真机（反馈者环境）

### 5. 实现（subagent）
spawn brief 必含：
- PRD 文件路径（单一事实来源）
- 分项 commit 要求（每 S 项一个）
- 测试先行
- 汇报格式
- **⚠️ 已知陷阱**：纯文本结尾的汇报会触发 daemon 判 needs_input → 回调丢失。
  workaround：brief 里要求汇报后附一个无操作工具调用，或 spawn 后 15 分钟主动查一次 session 文件（`~/.heart-portal/subagent/pi/sessions/<id>.jsonl` 尾部）。

### 6. Review
- 逐 commit 看 diff（git show）
- PRD 偏差当场标注：描述与代码块矛盾时，定哪边是权威（本次 S2：以代码块为准），当场改 PRD
- 测试全绿（`python3 tests/run_tests.py`）

### 7. 部署
`./kit/sync.sh`（语法检查 → rsync → 停旧进程）
→ `hand_health` 验证：uptime 归零（新进程）+ 版本号正确

### 8. Dogfood
真实场景全链路自测（本次：cdp_open → see dom → shot）。
版本号、manifest、import 三处一致性检查。

### 9. 发布
Grove publish：manifest 版本号、CHANGELOG 更新、发布说明。
发布后 Grove API 确认新版本可见。

### 10. 公告与验收
- 围炉/篝火 @ 相关反馈者，告知修复版本
- L3 真机验收（反馈者环境），验收通过后本迭代闭环

## 本次迭代（6.10.0）验证过的经验

1. **活证据 > 记忆重放**：全貌拉取时发现两处记忆与现实不符，以源码为准当场修正——这个动作模式已稳定
2. **PRD 偏差是正常的**：subagent 实现时发现 PRD 内部矛盾（S2），以代码块为准改 PRD——PRD 是活文档
3. **subagent 回调不可依赖**：完成通知会丢（needs_input 陷阱），关键迭代 spawn 后要主动查 session 文件
4. **review 双保险**：即使回调丢失，我按自己节奏 review 也不影响正确性——只是不知道交卷了会做两遍
